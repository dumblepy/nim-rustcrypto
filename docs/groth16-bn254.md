# Groth16 / BN254 verification

Module: `rustcrypto/algorithm/groth16` (marker type `Groth16Bn254`)

Verifies **Groth16 proofs over BN254** with `ark-groth16` 0.5.0 and `ark-bn254` 0.5.0.
This module is a **verifier only**; it does not generate proofs, circuits, or trusted
setup parameters.

Circuit construction and proof generation are available separately through
[`Groth16Bn254Prover`](groth16-prover.md). The verifier wire format remains unchanged.

## API

```nim
import rustcrypto/algorithm/bn254
import rustcrypto/algorithm/groth16

let vk: seq[byte] = ...       # v1 verifying key
let proof: seq[byte] = ...    # v1 proof (256 bytes)
let publicInputs = @[fromHexFr("...")]  # ordered circuit public inputs

if Groth16Bn254.verify(vk, proof, publicInputs):
  echo "valid for this verifying key"
```

Additional helpers:

- `Groth16Bn254.validateVerifyingKey(vk)` → `bool`
- `Groth16Bn254.validateProof(proof)` → `bool`

`verify` returns `false` only for a structurally valid proof that does not verify.
Malformed keys/proofs, non-canonical field elements, and public-input count mismatches
raise `ValueError`.

## Wire format v1

All integers are big-endian. Point encoding is defined in [bn254.md](bn254.md).

### Proof (exactly 256 bytes)

| Offset | Size | Field |
|---|---:|---|
| 0 | 64 | `A` (G1) |
| 64 | 128 | `B` (G2) |
| 192 | 64 | `C` (G1) |

### Verifying key

| Offset | Size | Field |
|---|---:|---|
| 0 | 8 | magic `"RCG16V1\0"` |
| 8 | 64 | `alpha_g1` (G1) |
| 72 | 128 | `beta_g2` (G2) |
| 200 | 128 | `gamma_g2` (G2) |
| 328 | 128 | `delta_g2` (G2) |
| 456 | 4 | `ic_count` (`u32`) |
| 460 | `64 * ic_count` | `ic[0..ic_count]` (G1 each) |

Total length is exactly `460 + 64 * ic_count`. `ic_count` must be `1..=4096`;
trailing bytes are rejected. The number of public inputs must be exactly
`ic_count - 1`, in the circuit's order.

### Public inputs

Each input is a 32-byte canonical big-endian `Fr`. The array length must equal
`ic_count - 1`; an empty array is allowed only when `ic_count == 1`.

## Validation and error behavior

- Proof and VK points must be canonical, on-curve, and in the prime-order subgroup.
- The point at infinity is accepted in proof points (mathematically valid) and
  **rejected** in verifying-key points.
- Non-canonical field coordinates and non-canonical public inputs are rejected.
- Length/format errors are distinguished from a mathematical verification failure:

| Status | Meaning |
|---|---|
| `RustCryptoOk` | Proof verified |
| `RustCryptoErrVerificationFailed` | Well-formed proof did not verify |
| `RustCryptoErrInvalidProofFormat` (22) | Wrong proof structure/length |
| `RustCryptoErrInvalidVerifyingKey` (23) | Wrong VK structure/header/length |
| `RustCryptoErrInvalidPublicInputCount` (24) | Input count ≠ `ic_count - 1` |
| `RustCryptoErrInvalidFieldElement` (20) | Non-canonical field element |
| `RustCryptoErrInvalidCurvePoint` (21) | Off-curve or wrong-subgroup point |

## Interoperability with Circom / snarkjs

`ark-serialize` is used internally only as an implementation detail; the wire format
above is the public contract. snarkjs JSON proofs/keys are **not** byte-compatible.

To convert a snarkjs artifact:

1. Decode decimal/hex field elements to 32-byte big-endian canonical `Fr`/`Fq`.
2. Encode G1 as `x || y`, G2 as `x.c0 || x.c1 || y.c0 || y.c1`.
3. Order the `IC` points exactly as in the snarkjs VK (`IC[0]` first).
4. Order public inputs exactly as the circuit's public signals (typically signal 1..n).
5. Reject any artifact with extra bytes.

The repository fixture is generated by an independent arkworks prover
(`rustcrypto-ffi/examples/groth16_fixture.rs`) with a deterministic seed, and committed
at `tests/fixtures/groth16_bn254_v1.hex`. Rust and Nim tests verify it and cover wrong
public inputs, tampered points, wrong magic, trailing bytes, and non-canonical values.

## Target support

Native Linux x86_64 / macOS arm64 and both wasm targets supported by this package
(`wasm32-unknown-unknown`, `wasm32-wasip1`) build the Groth16 verifier. Verification is
pure Rust and needs no OS randomness.

## Security notes

- A successful verification means the proof is valid **for the supplied verifying key**.
  It does **not** mean the circuit or the key is approved. Pin trusted VKs and their
  circuit versions in the application.
- Verifying keys and proofs from untrusted sources are bounded and validated
  (`ic_count <= 4096`, input count follows the key) to avoid unbounded allocations.
- `arkworks` is not audited by this project. The verifier is not a substitute for a
  protocol-level security review.
