# Halo2 verification (PSE/Axiom KZG / BN254 / SHPLONK / Blake2b)

Module: `rustcrypto/algorithm/halo2` (marker type `Halo2KzgBn254`)

> **Fixed Halo2 profile.** Halo2 is not a single proof format. This module accepts only
> the profile below. Zcash `halo2_proofs` IPA/Pasta proofs, PSE Poseidon-transcript
> proofs, EVM/Keccak-transcript proofs, and gnark PLONK proofs are different and are
> rejected.

## Profile (v1)

| Item | Value |
|---|---|
| Implementation | `snark-verifier` 0.2.7 over `halo2-axiom` 0.5.3 (PSE-halo2 derivative) |
| Curve / field | BN254, `Fr` |
| PCS | KZG with a universal SRS |
| Multi-open | **SHPLONK** (`snark_verifier::pcs::kzg::Bdfg21`) |
| Fiat-Shamir | halo2 `Blake2bRead` / `Blake2bWrite`, `b"Halo2-Transcript"`, 64-byte challenges |
| Protocol encoding | `bincode` 1.3.3, fixed-int, of `PlonkProtocol<G1Affine>` |
| Verifier | `PlonkVerifier<KzgAs<Bn254, Bdfg21>>` + `KzgDecidingKey<Bn254>` |

Why not Zcash IPA/Pasta: the Zcash `halo2_proofs` 0.3/0.4 API does not expose a
circuit-independent verifying-key deserializer, so a generic "verify with external
VK bytes" API cannot be built on it without reimplementing the verifier or pinning a
concrete circuit. The PSE/Axiom KZG profile exposes a data-only `PlonkProtocol` and is
therefore used here.

## API

```nim
import rustcrypto/algorithm/halo2

let params: seq[byte] = ...          # v1 SRS subset
let vk: seq[byte] = ...              # v1 protocol
let proof: seq[byte] = ...           # Blake2b SHPLONK proof bytes
let publicInstances: seq[byte] = ... # v1 instance columns

if Halo2KzgBn254.verify(params, vk, proof, publicInstances):
  echo "valid for this profile, SRS, and key"
```

Helpers: `validateParams`, `validateVerifyingKey`, `validatePublicInstances`.

`false` means structurally valid but not verifying. Malformed blobs, non-canonical
field values, mismatched instance columns, and trailing bytes raise `ValueError`.

## Wire format v1

### Params — SRS subset (exactly 328 bytes)

| Offset | Size | Field |
|---|---:|---|
| 0 | 8 | magic `"RCH2P1\0\0"` |
| 8 | 64 | `[1]_1` (G1) |
| 72 | 128 | `[1]_2` (G2) |
| 200 | 128 | `[tau]_2` (G2) |

Points use the canonical big-endian encoding from [bn254.md](bn254.md). Points must be
on-curve and in the prime-order subgroup; infinity is rejected.

### Verifying key

| Offset | Size | Field |
|---|---:|---|
| 0 | 8 | magic `"RCH2V1\0\0"` |
| 8 | 4 | `protocol_len` (`u32` BE, 1..=2 MiB) |
| 12 | `protocol_len` | `bincode(PlonkProtocol<G1Affine>)` |

Protocol deserialization is bounded to 2 MiB and rejects trailing bytes. Before the
verifier runs, the protocol is checked for bounded instance/witness/challenge counts,
chunk degree, query count, duplicate query/evaluation keys, query polynomial indices
(including the quotient slot), bounded rotations, consistent instance-query keys, and
in-range accumulator indices. `domain_as_witness` and non-v1 linearization slots are
rejected. Every protocol G1 commitment (preprocessed and instance-committing) is
validated on-curve and in the prime-order subgroup. These checks close panic paths that
a hostile protocol could otherwise reach inside `snark-verifier`
(`evaluations.remove(query).unwrap()`, instance indexing, zero chunk degree).

### Public instances

| Offset | Size | Field |
|---|---:|---|
| 0 | 8 | magic `"RCH2I1\0\0"` |
| 8 | 4 | `column_count` (`u32` BE, ≤ 64) |
| 12 | — | repeated columns |

Each column:

| Size | Field |
|---|---|
| 4 | `value_count` (`u32` BE) |
| `value_count * 32` | canonical big-endian `Fr` values |

The total number of values is bounded at `2^20`. There must be exactly one column per
protocol instance polynomial, with exactly the expected number of values in each.
Trailing bytes are rejected.

### Proof

Raw bytes written by halo2's `Blake2bWrite` transcript for the **SHPLONK** prover.
Proof length is bounded at 16 MiB. The verifier reads the proof with a counting reader
and rejects trailing bytes.

## Fixtures and tests

`rustcrypto-ffi/examples/halo2_fixture.rs` builds a small halo2-axiom circuit (an advice
cell constrained equal to one public instance), generates `ParamsKZG::setup(8, rng)` with
a **seeded, test-only SRS**, and writes the v1 params/VK/proof/instances. The fixture is
committed at `tests/fixtures/halo2_kzg_bn254_v1.hex`.

The multi-instance fixture `tests/fixtures/halo2_kzg_bn254_multi_v1.hex` is generated by
`rustcrypto-ffi/examples/halo2_fixture_multi.rs`: K=10, two advice columns, two instance
columns with two public values each (`num_instance = vec![2, 2]`), the same seeded SRS,
and a native halo2-axiom `verify_proof` check before the fixture is written. It is
covered by `rustcrypto-ffi/tests/halo2_multi_fixture.rs` and
`tests/algorithm/test_halo2_multi.nim`. The fixture is a committed artifact:
re-running the generator produces a freshly randomized (but valid) `PROOF`, so
regeneration is not byte-identical for that line.

Tests cover successful verification plus modified instances, modified proofs, modified
params, modified verifying keys, truncated/trailing/failed-length blobs, wrong column
layouts, non-canonical instance values, NULL pointers, zero lengths, and repeated calls.
`rustcrypto-ffi/tests/halo2_robustness.rs` adds a deterministic bounded mutation fuzz
(2000 iterations) over all four blobs and asserts the C ABI never returns
`RUSTCRYPTO_ERR_PANIC`; a focused regression test pins the mutated protocol query that
previously panicked.

The same fixture is exercised through the C ABI by
`rustcrypto-ffi/examples/halo2_verify.rs` and
`rustcrypto-ffi/examples/halo2_verify_web.rs`:

| Target | How it is executed | Result |
|---|---|---|
| Native Linux x86_64 | `cargo run --example halo2_verify` | positive + negative checks pass |
| `wasm32-wasip1` | `wasm32-wasip1` example under Node 24 `node:wasi` | positive + negative checks pass |
| `wasm32-unknown-unknown` | cdylib example instantiated by Node 24 `WebAssembly` | positive + negative checks pass |

`ci/test_halo2_wasm.sh` builds both archives, checks the four Halo2 symbols with
`llvm-nm`, and runs the native and both wasm smoke tests. The wasm runtimes above are
the environments this repository actually executes; other wasm hosts are not claimed.
GitHub Actions runs this script in the `ZKP integration` job (with
`environment.txt` / `symbols.txt` artifacts). `test.sh`, used by the Linux Docker and
macOS jobs, runs the generic Rust/Nim suites (which include native Halo2 unit and
integration tests) and builds both wasm archives, but does not repeat this dedicated
C ABI example smoke.

Measured raw archive sizes in this build: Linux x86_64 49,496,168 bytes,
`wasm32-unknown-unknown` 33,142,524 bytes, `wasm32-wasip1` 32,237,204 bytes. wasm
verification timing and memory were not measured.

## Target support

| Target | Build | Execute |
|---|---|---|
| Linux x86_64 | yes | yes (Nim + Rust tests) |
| macOS arm64 | yes | yes (Nim + Rust tests) |
| `wasm32-unknown-unknown` | yes | yes (fixture smoke in Node `WebAssembly`) |
| `wasm32-wasip1` | yes | yes (fixture smoke in Node WASI) |

Both wasm archives export the four `rustcrypto_halo2_kzg_bn254_*` symbols. The Nim
marker API (`Halo2KzgBn254.verify` and the `validate*` helpers) resolves to these
symbols on wasm targets, including through the umbrella `rustcrypto` module. The
executed wasm smoke tests above call the Rust C ABI directly; a Nim-generated wasm
executable was not built or run in this repository.

### wasm build note (vendored patch)

Upstream `halo2-axiom` 0.5.3 enables its `multicore` feature by default, which is a hard
compile error on wasm32 without atomics. This repository vendors the crate at
`rustcrypto-ffi/third_party/halo2-axiom-0.5.3` with only the default feature list
changed (`multicore` removed); see `rustcrypto-ffi/third_party/PATCH.md` for the exact
diff, checksum, license, and update procedure. Native builds re-enable `multicore`
through a target-specific dependency, so native verification keeps the parallel path.
The verifier's execution path needs no entropy, OS I/O, filesystem, clock, or WASI
syscalls. `rayon` 1.12+ supplies a single-threaded fallback on wasm for the remaining
direct `rayon` uses in the dependency graph.

The wasm profile is sequential. Proof verification, transcript, KZG pairing, subgroup
checks, and public-input binding are unchanged.

## Security notes

- The SRS and verifying key (circuit) are caller-supplied. Trusting them, and binding
  them to an approved circuit/version, is the application's responsibility.
- This profile requires a KZG trusted setup. The fixture SRS is deliberately insecure
  and must never be used for production.
- `snark-verifier` / `halo2-axiom` are not audited by this project.
- The API verifies the pairing equation and PLONK constraints; it does not prove that
  the circuit represents a meaningful application statement.
- Both wasm targets use `panic = "abort"`, so `catch_unwind` cannot turn a panic into an
  error code. Input length, canonical field, curve/subgroup, instance-shape, and
  protocol-shape checks run before the proof-system library; malformed
  params/VK/proof/instances return the documented status codes or `false`, not a panic
  in the tested cases. The bounded mutation fuzz in
  `rustcrypto-ffi/tests/halo2_robustness.rs` is the regression gate for this contract.
- The verifying key (circuit) and SRS remain trusted inputs. The structural checks are
  defensive, not a substitute for pinning an approved VK/SRS. bincode nested-value
  recursion is bounded by the 2 MiB protocol limit but not by a separate recursion-depth
  counter; a fully adversarial VK is outside the trusted-input model.
